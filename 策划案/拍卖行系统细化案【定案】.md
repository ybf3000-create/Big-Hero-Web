# 拍卖行系统细化案 v1.3【定案】

> 本案面向最大同时在线20人的熟人小服，只支持卖家定价的一口价交易。
>
> Q27~Q34已全部确认。费用定案见§6.2：创建订单免费，成交后扣成交价5%手续费。

---

## 1. 设计目标与范围

| 类型 | 内容 |
|------|------|
| 目标 | 玩家可异步出售和购买指定范围的装备、宝石及打孔器 |
| 目标 | 同一件物品任何时刻只有一个所有者或一个托管状态 |
| 目标 | 卖家离线时仍可成交，买卖双方上线后可查看结果 |
| 目标 | 所有金币、物品和订单变化均由服务端决定并可审计 |
| 非目标 | 不做玩家面对面交换、赠送金币或指定买家交易 |
| 非目标 | 不做拍卖聊天卡片、市场机器人或系统生成订单 |
| 非目标 | 不计算参考价值，不要求玩家按建议价出售 |

总纲[[GDD-走格子挂机游戏-总纲草案]] §1的柱6“玩家经济”已按[[联网规则基线与冲突处理表【已同步】]] C01恢复；旧案中的失效规则不再继承。

> 设计柱检验：异步交易支持柱2“Build深度”和柱6“玩家经济”；交易不要求双方同时在线，符合柱1“挂机爽感”和柱5“不肝不氪”。

## 2. 固定名称与状态

### 2.1 固定名称

| 名称 | 唯一定义 |
|------|---------|
| 拍卖订单 | 卖家把一件装备或一组同状态物品公开出售的记录 |
| 一口价 | 买家支付订单指定总价后立即成交的价格 |
| 拍卖仓库 | 每个角色独立的30格服务端仓库，用于订单托管和待领取物品 |
| 订单托管 | 上架物已移出普通背包，只能由订单流程改变状态 |
| 待领取 | 订单结束后物品仍在拍卖仓库，等待玩家转入普通背包 |
| 交易绑定 | 物品经拍卖成交后永久不能再次上架的状态 |
| 金币流水 | 每次金币扣除、转移和手续费销毁的只追加记录 |

### 2.2 订单状态

```text
ACTIVE（出售中）
  ├─ 买家购买成功 → SOLD（已成交）
  ├─ 到达结束时间 → EXPIRED（已到期）
  └─ 卖家主动取消 → CANCELLED（已取消）

SOLD / EXPIRED / CANCELLED均为终态，不可恢复为ACTIVE。
重新出售必须创建新订单编号。
```

### 2.3 物品位置

```text
普通背包
  └─ 上架成功 → AUCTION_ESCROW（卖家拍卖仓库中的订单托管）

AUCTION_ESCROW
  ├─ 成交 → AUCTION_CLAIMABLE（买家拍卖仓库，交易绑定）
  ├─ 到期 → AUCTION_CLAIMABLE（卖家拍卖仓库）
  └─ 取消 → AUCTION_CLAIMABLE（卖家拍卖仓库）

AUCTION_CLAIMABLE
  └─ 领取成功 → 普通背包
```

物品实例由服务端生成64位唯一编号或UUID。客户端本地递增编号不能用于联网所有权。

## 3. 可交易物品与绑定

### 3.1 可交易范围

| 类型 | 是否可上架 | 规则 |
|------|-----------|------|
| 套装装备 | 是 | 不限品质，但必须是玩家自己掉落且未交易绑定 |
| 传说装备 | 是 | 不论是否套装，但必须未交易绑定 |
| 宝石 | 是 | 等级和类型以[[背包道具货币系统案【定案】]]的有效配置为准 |
| 打孔器 | 是 | 文档和代码统一使用名称“打孔器” |
| 普通非套装、非传说装备 | 否 | 服务端拒绝 |
| 其他材料、天命卡、合成券等 | 否 | 服务端拒绝 |
| 金币 | 否 | 只能作为订单支付货币，不能直接赠送或上架 |

### 3.2 上架资格检查

```text
Step 1 服务端读取物品及当前所有者
  ├─ 属于当前角色 → Step 2
  └─ 不属于、记录不存在 → 拒绝
Step 2 检查物品位置和操作状态
  ├─ 位于普通背包且未锁定、未处理中 → Step 3
  └─ 已装备、已锁定、已托管或处理中 → 拒绝
Step 3 检查类型和交易绑定
  ├─ 属于可交易类型且未交易绑定 → Step 4
  └─ 类型不允许或已交易绑定 → 拒绝
Step 4 检查装备宝石
  ├─ 没有镶嵌宝石 → 进入价格和容量校验
  └─ 仍有镶嵌宝石 → 拒绝，要求玩家先拆下宝石
```

### 3.3 成交后的永久绑定

| 场景 | 处理 |
|------|------|
| 买到装备 | 装备实例标记`TRADE_BOUND`，可装备、强化槽位、镶嵌和分解，但不能再次上架 |
| 买到宝石 | 宝石标记交易绑定；镶嵌后再拆下仍保持交易绑定 |
| 买到打孔器 | 道具标记交易绑定，可正常消耗，不能再次上架 |
| 绑定与未绑定堆叠物 | 不合并为同一堆，避免丢失绑定状态 |
| 分解交易绑定装备 | 产出的可交易材料继承交易绑定，避免通过分解绕过限制 |
| 卖家订单到期或取消 | 原物退回卖家，不新增交易绑定 |

交易绑定只限制再次交易，不等于玩家手动“锁定”。锁定用于防误操作，可以解除；交易绑定不可解除。

> 设计柱检验：允许第一次流通帮助玩家补齐Build；成交后绑定抑制倒卖。该限制削弱柱6的重复流通，但属于ybf已确认的取舍。

## 4. 拍卖仓库与容量

### 4.1 固定容量

| 项目 | 规则 | 达到边界后的处理 |
|------|------|----------------|
| 每角色拍卖仓库 | 30格，不扩容 | 满时不能购买或新增上架 |
| 同时有效上架 | 最多3单 | 已有3单时拒绝第4单 |
| 上架时长 | 8、12、24小时三选一 | 其他值拒绝 |
| 装备 | 每件占1格 | 不可批量放入同一格 |
| 宝石、打孔器 | 同类型、同等级、同绑定状态按原堆叠上限占格 | 超过单格上限时必须减少数量或拆为多个订单 |
| 待领取期限 | 不过期 | 长期不领取继续占格，满仓后无法继续交易 |

拍卖仓库同时计算托管物和待领取物。订单从托管变成卖家待领取时仍占原格，不会造成第31格溢出。

### 4.2 容量成功与失败

| 操作 | 成功条件 | 失败处理 |
|------|---------|---------|
| 上架 | 有空仓库格且有效订单少于3 | 不移动物品，不创建订单 |
| 购买 | 买家至少有1个适配的空格或可合并格 | 不扣金币，订单保持出售中 |
| 领取 | 普通背包有空格或可合并 | 留在拍卖仓库，不丢失 |
| 一键领取 | 按订单结束时间从旧到新逐件处理 | 背包满时停止，已领取部分不回滚 |

## 5. 上架流程

### 5.1 上架参数

| 参数 | 规则 |
|------|------|
| 物品 | 从普通背包选择一件装备或一组可交易物品 |
| 数量 | 装备固定1；堆叠物为1至当前合法持有量及单格上限 |
| 一口价 | 卖家填写该订单的总价，必须是整数金币 |
| 价格范围 | `1 ~ 9,000,000,000,000,000`金币，并且不超过金币字段上限 |
| 时长 | 8、12、24小时三选一 |

系统不根据EqTier、品质、套装、词条、孔数或历史成交计算建议价。客户端可以保留玩家上次输入作为便捷默认值，但服务端不把该值视为物品价值。

### 5.2 原子上架

```text
Step 1 校验会话、角色归属和请求编号
Step 2 校验物品所有权、可交易范围、交易绑定和镶嵌状态
Step 3 校验数量、价格、时长、3单上限和30格容量
Step 4 开启数据库事务，锁定角色、物品和拍卖仓库格
Step 5 再次校验
  ├─ 全部成立 → 物品转入订单托管，创建订单和流水，提交
  └─ 任一不成立 → 整体回滚
Step 6 返回服务端订单快照
```

堆叠物只出售部分数量时，拆分和托管必须在同一事务完成；失败时原堆叠数量保持不变。

### 5.3 失败分支

| 原因 | 处理 |
|------|------|
| 物品不属于角色或状态已变化 | 拒绝并刷新该物品状态 |
| 物品类型不允许或已绑定 | 拒绝并显示具体限制 |
| 装备仍有宝石 | 拒绝并提示先拆下 |
| 数量为0、负数或超过持有量 | 拒绝，不拆分物品 |
| 价格非整数或越界 | 拒绝并保留输入内容 |
| 有效订单达到3单或仓库已满 | 拒绝，不移动物品 |
| 数据库失败 | 事务回滚，不留下半成品订单 |
| 请求超时后重试 | 同一请求编号返回第一次结果，不重复上架 |

## 6. 卖家定价与费用

### 6.1 定价规则

卖家独立填写一口价。系统只检查整数、正数和金币字段上限，不评价价格高低，也不根据物品属性拦截高价或低价订单。

价格明显异常时只写入审计标记，管理员可查看；不会自动改价、自动成交或自动处罚。卖家不能购买自己的订单。

### 6.2 定案费用

采用以下规则：

| 项目 | 定案规则 | 成功与失败 |
|------|---------|-----------|
| 创建订单费用 | 0金币 | 上架和取消均不扣金币 |
| 成交手续费 | `floor(成交价 × 5 / 100)` | 仅成交成功后从成交额扣除；交易失败不扣 |
| 卖家到账 | `成交价 - 成交手续费` | 与成交事务同时到账，不能出现负数 |
| 1~19金币订单 | 手续费因向下取整为0 | 卖家获得全部成交价 |

定案理由：20人熟人服市场可能较冷，免费创建订单不会因流拍持续惩罚卖家；只在真实成交时回收5%金币，规则容易理解和核对。

客户端只展示服务端计算结果，不能自行改变费率。费率后续若调整，必须升级规则版本并保留旧订单成交时适用的费率快照。

### 6.3 经济验证

开发完成后，以[[数值设计总表]] v3.6为基线模拟20个角色连续90天，覆盖0%、25%、50%、100%交易参与率和长期无人交易五种情况。记录金币总产出、原系统消耗、交易额、手续费回收量和角色金币中位数。

费用验证只用于观察经济结果，不生成物品价格建议，也不修改玩家填写的订单价格。

> 设计柱检验：免费创建订单降低小服试价成本，成交后收费只对完成交易生效；5%费率需通过90天模拟复核不会破坏柱5和柱6。

## 7. 一口价购买与成交

```text
Step 1 买家提交订单编号和幂等请求编号
Step 2 服务端锁定订单、买家金币、卖家、物品和双方仓库状态
Step 3 校验订单仍为出售中、未到期、买家不是卖家、买家容量和金币足够
Step 4 原子执行
  买家扣除成交价
  卖家增加净到账
  系统记录并销毁已确认的手续费
  物品从卖家托管转入买家待领取并标记交易绑定
  订单变为已成交
  写入订单、金币、物品流水
Step 5 提交后通知双方
```

| 并发或失败场景 | 结果 |
|---------------|------|
| 两名买家同时购买 | 只有先锁定并提交的一笔成功，另一笔返回“订单已结束” |
| 买家金币不足 | 不扣金币、不移动物品 |
| 买家拍卖仓库已满 | 不扣金币，订单保持出售中 |
| 卖家离线 | 正常成交和到账，卖家下次登录可见通知 |
| 通知发送失败 | 不回滚已提交成交；重连或上线后补读结果 |
| 数据库事务失败 | 整笔回滚，订单、金币和物品恢复原状态 |
| 响应丢失 | 相同请求编号返回原结果，不再次扣款或发货 |

成交提交后，卖家原托管格释放，买家占用一个待领取格。双方容量变化必须与订单状态在同一事务内完成。

## 8. 到期、取消与领取

### 8.1 到期

订单到达服务端结束时间且仍为出售中时，变为已到期，原物转为卖家待领取。没有买家、服务器重启或卖家离线都不会丢失物品。

定时任务每10秒处理一批最多100个到期订单。全服最多20个在线角色、每角色3个有效订单，正常上限为60单；单批容量可覆盖全部活跃订单。

### 8.2 取消

卖家可以在订单成交前随时取消。取消成功后订单成为终态，物品转为卖家待领取；取消失败时订单和物品保持原状。由于创建订单免费，取消不产生退款或罚金。

### 8.3 领取

| 场景 | 处理 |
|------|------|
| 普通背包有容量 | 物品从待领取转入普通背包并写物品流水 |
| 普通背包无容量 | 领取失败，物品继续留在拍卖仓库 |
| 重复点击或网络重试 | 相同请求编号只执行一次 |
| 领取绑定物 | 交易绑定状态保持不变 |
| 待领取物达到30格 | 不丢弃，但禁止新购买和上架，直到腾出空间 |

服务重启后扫描所有结束时间已过但仍为出售中的订单，按每批100单补处理；单笔失败只重试该订单，不阻塞其他订单。

## 10. 事务、守恒与幂等

### 10.1 金币守恒

按§6.2定案费用，每笔成交必须满足：

```text
买家金币减少 = 成交价
卖家金币增加 = 成交价 - 成交手续费
系统销毁金币 = 成交手续费
买家变化 + 卖家变化 + 系统变化 = 0
```

成交价为1~19金币时，向下取整后的手续费为0；卖家增加量等于成交价，守恒公式仍成立。

### 10.2 物品守恒

```text
成交前物品实例数量 = 成交后物品实例数量
一次成交的所有权迁移次数 = 1
同一物品最多存在一个出售中订单
订单托管物不可装备、分解、锁定切换、镶嵌、打孔或再次上架
```

所有改变资产的请求必须携带`request_id`。服务端保存请求结果；相同账号、命令类型和请求编号的重试只返回第一次结果。

## 11. 安全、审计与管理边界

| 风险 | 处理 |
|------|------|
| 客户端伪造物品、价格或金币 | 服务端从数据库读取并重新校验，忽略客户端资产字段 |
| 重复购买或重复发货 | 幂等请求、SQLite短写事务锁、唯一流水键 |
| 卖家购买自己的订单 | 服务端拒绝 |
| 用绑定物绕过限制 | 上架检查绑定状态；堆叠和分解按§3.3传播绑定 |
| 异常高价转移金币 | 不自动估值或处罚，只记录价格、双方和时间供管理员查看 |
| 托管期间改造物品 | 位置状态约束和事务拒绝其他操作 |
| 管理员误操作 | 管理工具不能直接发金币或装备；所有状态操作写审计 |

| 记录 | 留存 |
|------|------|
| 玩家可见交易记录 | 90天 |
| 订单事件 | 180天 |
| 金币、物品和管理审计流水 | 至少1年 |
| 已结束订单物品快照 | 至少1年 |

每日批量执行金币与物品守恒检查。发现异常时标记相关记录并通知管理员，不自动制造金币或补发复制物品。

## 12. 数据结构概要

| 表 | 关键字段 | 关键约束 |
|----|---------|---------|
| `equipment_instances` | id、owner_character_id、location、trade_bound、revision、data | id全局唯一；位置和绑定受约束 |
| `item_stacks` | id、owner_character_id、item_type、level、quantity、trade_bound、location | 数量为正；不同绑定状态不得合并 |
| `auction_listings` | id、seller_id、item_ref、quantity、buyout_price、status、expires_at、rules_version | 一个物品引用最多一个出售中订单 |
| `auction_warehouse_slots` | character_id、slot_index、item_ref、slot_state、listing_id | 角色内槽位1~30唯一 |
| `gold_ledger` | id、character_id、delta、reason、reference_id、balance_after | 只追加；同一引用动作唯一 |
| `item_ledger` | id、item_ref、from_owner、to_owner、from_location、to_location、reference_id | 只追加；成交迁移唯一 |
| `auction_events` | listing_id、event_type、actor_id、created_at、payload | 只追加，用于恢复和审计 |

金币、价格和手续费均使用64位整数，不使用浮点数。百分比费用使用整数乘法后向下取整，客户端只展示服务端结果。

## 13. 性能与故障恢复

| 项目 | 目标或处理 |
|------|-----------|
| 规模上限 | 20名同时在线角色，最多60个出售中订单 |
| 普通搜索 | P95小于200ms，最终以Windows部署机压测为准`[需与程序确认]` |
| 购买事务 | P95小于1秒，最终以部署机压测为准`[需与程序确认]` |
| 数据库暂时不可用 | 查询显示暂不可用；资产操作全部失败并回滚 |
| 服务重启 | 补处理到期订单，不回滚已提交成交 |
| 通知服务失败 | 成交结果保留，玩家上线后按订单事件补读 |
| 备份恢复 | 订单、物品、金币和流水必须恢复到同一一致时间点 |

压测至少覆盖两人同时购买同一订单、60单同时到期、重复请求、仓库满、金币恰好等于价格和金币为0等边界。

## 14. 随机算法说明

上架、搜索、购买、到期、取消、领取和费用均为确定性规则，不使用随机算法。首版不创建任何系统订单，因此没有随机选品、随机价格或刷新概率。

## 16. 设计柱检验

| 决策 | 设计柱 | 检验 |
|------|--------|------|
| 只做一口价异步成交 | 柱1、柱5、柱6 | 不要求盯盘，同时建立玩家市场 |
| 只交易精品与关键材料 | 柱2、柱3 | 支持Build成型，普通掉落仍按原循环消化 |
| 成交后永久绑定 | 柱3、柱6 | 保留首次流通并限制倒卖；接受重复流通下降的代价 |
| 槽位强化不随装备交易 | 柱2、柱6 | 保持角色长期成长，避免把角色强化错误计入物品 |
| 无系统订单、无参考估值 | 柱3、柱6 | 市场价格完全来自玩家供需，不稀释Boss掉落价值 |
| 服务端托管和守恒审计 | 柱6 | 防复制和重复扣款，维持资产可信 |

总纲已恢复柱6“玩家经济”；成交后永久绑定仍会降低重复流通，但这是 ybf 确认用于限制倒卖的取舍。
