> - [[聊天系统细化案【定案】]]
> - [[拍卖行系统细化案【定案】]]

## 1. 项目通读结论（2026-09-11改造前基线）

本章保留改造前事实，不代表当前开发状态；当前进度见§9.2。后续唯一客户端范围见§3.3。

### 1.1 当前项目形态

| 项目 | 当前事实 | 联网目标差距 |
|------|---------|-------------|
| 客户端 | Godot 4.4，主场景为 `select_slot.tscn` | 需增加 Web 导出、登录场景、断线恢复和网络状态 UI |
| 角色数据 | `SaveManager` 把 3 个槽位写入本地 `user://saves/slot_0~2.json` | 需迁移为账号、角色和资产数据库记录 |
| 核心逻辑 | 地图、随机、战斗、掉落、金币、背包均在客户端执行 | 价值结果必须迁到服务端权威执行 |
| 服务端 | `SERVER` 目录为空 | 需从零建立接口、实时连接、数据库、后台任务和部署脚本 |
| 网络功能 | 无账号、协议、聊天、拍卖行、在线人数管理 | 三个系统均为新开发 |
| Web 配置 | 无 `export_presets.cfg` | 需新增 Web 构建与浏览器兼容验证 |
| 自动测试 | 有战斗、装备、套装词缀、新玩家平衡 4 组回归脚本 | 需保留，并新增服务端、接口、并发和端到端测试 |

### 1.3 开发进度口径

| 口径 | 结论 |

## 3. 已确认产品边界

### 3.1 首版范围

| 范围 | 推荐首版 | 不在首版 |
|------|---------|---------|
| 浏览器 | 桌面 Chrome/Edge 最近两个主版本 | 手机浏览器完整适配、Safari专项适配 |
| 联机关系 | 每名玩家保留自己的地图与挂机进度；只共享聊天和拍卖行 | 同屏共享地图、共享在线资料、组队战斗、PVP |
| 人数 | 同时保持游戏会话的账号最多 20 个 | 20 人同场景同步移动 |
| 账号 | 邀请码自动注册、账号密码登录、每账号1角色 | 邮箱、手机、人工审批、第三方登录 |
| 交易 | 仅一口价异步交易，成交物永久绑定 | 竞价、面对面交换、赠送金币、系统托底 |
| 运维 | 单服、单区、单数据库 | 多区服、跨服市场 |

> 设计柱检验：个人挂机地图保留柱1“挂机爽感”和柱4“格子策略”；共享聊天与市场恢复柱6“玩家经济”，且不引入强制组队，不破坏柱5“不肝不氪”。

### 3.2 明确不应沿用的单机做法

| 单机做法 | 联网风险 | 联网处理 |
|---------|---------|---------|
| 客户端直接增加金币/经验 | 修改内存或请求内容即可作弊 | 客户端只发操作意图，服务端计算并落库 |
| 客户端用 `randi/randf` 决定掉落 | 可重放、篡改或预知随机 | 价值随机统一在服务端发生 |
| 客户端上传整份存档覆盖服务端 | 可复制装备、回滚消费 | 使用细粒度命令和事务，不接受客户端资产快照 |
| 本地递增装备 `uid` | 重启后可重复，跨账号冲突 | 服务端生成全局唯一装备实例编号 |
| 用本机时间算离线时长 | 修改系统时间可刷收益 | 只使用服务端时间 |
| 请求失败直接重试写操作 | 可能重复扣款或重复发奖 | 每个价值操作带幂等请求编号 |

### 3.3 唯一客户端与还原约束（2026-09-16确认）

| 项目 | 已确认范围 | 不满足时的处理 |
|------|------------|----------------|
| 开发引擎 | 继续使用Godot 4.4，游戏功能在`client/`的GDScript、场景与素材中开发 | 不改成手写HTML游戏，不恢复已停用的`web-client/`为玩家入口 |
| 玩家客户端 | 只开发、发布和验收Godot Web浏览器客户端，首版浏览器范围沿用§3.1 | 不再开发、发布或验收桌面原生Godot客户端；手机专项适配仍不在首版 |
| 原版复用 | 原版UI、透视大地图、逐格移动、装备、技能和战斗表现为还原基准，规则以对应定案为准 | 原版与定案冲突时指出具体文档章节、代码或画面后讨论，不自行简化或改数值 |
| 浏览器差异 | 网络、存储和输入适配服务于原版还原，不改变玩法与默认奖励 | 浏览器能力不足或表现不明确时先讨论替代方案，不静默删功能或新增道具 |
| 旧桌面与本地代码 | 暂留作历史参考，可复用的规则回归继续保留 | 不新增桌面兼容分支，不要求修复只影响停用桌面入口的问题，不删除可复用核心逻辑 |
| 验收与发布 | 源码变更后重新Web导出、兼容检查、自动测试和真实浏览器自测，通过后上传Git | 编辑器或原生程序运行成功不能替代Web验收；失败时不发布旧包冒充新功能 |

> 设计柱检验：复用原版保护柱2的Build深度和柱4的格子策略；唯一浏览器交付减少柱5的维护负担；服务端权威边界继续保护柱6，不因停止桌面维护而放宽资产可信性。

## 4. 已确认技术架构

### 4.1 结构

```text
浏览器
  └─ Godot Web 客户端
       ├─ HTTP/HTTPS：注册、登录、角色读取、背包、拍卖查询
       └─ WS/WSS：在线会话、聊天、状态通知、拍卖成交推送

同源入口（ZeroTier私网HTTP；未来公网HTTPS）
  └─ 单体游戏服务
       ├─ 账号与会话
       ├─ 角色命令与服务端规则
       ├─ 聊天房间
       ├─ 拍卖事务
       └─ 定时任务（离线、拍卖到期、清理）
            └─ SQLite数据库文件
                 ├─ 账号/角色
                 ├─ 资产/装备实例
                 ├─ 会话/审计
                 ├─ 聊天记录
                 └─ 拍卖订单/金币流水
```

### 4.2 技术选择建议

| 层 | 推荐 | 理由 | 备选 |
|----|------|------|------|
| 网页客户端 | Godot 4.4无多线程Web导出，唯一客户端 | 最大化复用当前UI、地图、战斗表现和素材，不再维护桌面交付 | 已确认，边界见§3.3 |
| 服务端 | TypeScript 单体服务 | 账号、WebSocket、数据库和测试生态成熟；20 人无需微服务 | Godot Headless，逻辑复用高但安全/数据库生态弱 |
| 数据库 | SQLite（WAL模式） | 20人单进程小服足够；支持事务、唯一约束、外键和审计，无需独立数据库服务 | 若未来需要多个服务进程或多台服务器，再迁移PostgreSQL |
| 服务器 | Windows 自有电脑 | 符合现有条件，首版单机部署 | 后续可迁移Linux而不改变协议 |
| 当前网络入口 | 已授权的同一ZeroTier私网中的HTTP/WS地址 | ZeroTier提供加密虚拟网络，玩家可直接用浏览器访问 | 真正公网开放必须使用可信HTTPS/WSS，不能直接暴露明文登录入口 |
| 入口服务 | TypeScript服务同端口发布Web文件、接口与WebSocket | 玩家只访问一个地址，不需证书或额外命令 | 未来公网部署增加Caddy或穿透服务的可信TLS入口 |
| 缓存 | 首版不引入 Redis | 20 人规模数据库即可承载 | 以后达到测量阈值再加 |

Godot 4.4无多线程Web包已通过ZeroTier地址普通HTTP启动验证。`client/tools/patch-web-export.mjs`负责安全上下文与音频后备兼容；重新导出后必须执行补丁与检查。音频实际播放、完整玩法持久化及跨机访问仍须分别验收，不能只按编辑器运行结果判断。

### 4.3 自有服务器与ZeroTier入口

```text
朋友的电脑（已安装、加入并获准使用同一ZeroTier网络）
  → 浏览器打开 http://服务器的ZeroTier地址:端口/game/
  → ZeroTier加密虚拟网络
  → Windows 自有服务器
       ├─ Web 静态文件
       ├─ TypeScript 游戏服务
       └─ SQLite（仅游戏服务读写，不直接暴露公网）
```

当前首版不要求域名或HTTPS证书，使用ZeroTier私网HTTP/WS与无多线程Godot Web导出。ZeroTier地址不是公网IP；另一台电脑必须加入并获准使用同一网络。服主预先配置服务器监听与防火墙，之后玩家直接用浏览器打开地址，无需安装证书或执行额外命令。未加入、未授权、服务离线、端口错误或防火墙阻断时无法访问，服主检查对应配置，不自动回退到明文公网入口。

若未来允许不安装ZeroTier的电脑从真正公网访问，则必须另外配置浏览器信任的HTTPS证书与WSS；当前私网HTTP兼容不能替代公网传输安全。

SQLite运行库固定使用WAL、外键、5秒写锁等待和强同步；资产操作使用短写事务，同一时刻只运行一个游戏服务进程。运行库与在线备份均放在OneDrive之外；若数据库文件不可写或事务失败，本次注册、金币、物品或订单操作整体失败，不保留半成品。

> 设计柱检验：SQLite降低20人熟人服的部署维护负担，符合柱5；短事务、唯一约束和独立备份继续保护柱2与柱6的角色资产和玩家经济。

### 4.4 服务端权威边界

联网版的服务器是唯一规则与资产权威。客户端只发送玩家的操作意图，不能提交掷骰点数、随机种子、战斗伤害、掉落物、金币、经验或完整存档覆盖数据。服务器执行原版 Godot 的地图、战斗、装备、技能、天气、彩票和掉落规则，生成结果并以事务方式保存；客户端只负责还原原版表现和展示服务器结果。

| 服务端必须决定 | 客户端可以决定 |
|---------------|---------------|
| 账号身份、在线名额、角色归属 | UI 布局、动画、音效 |
| 金币、经验、等级、背包容量 | 筛选条件和本地排序展示 |
| 装备生成、唯一编号、词条和掉落 | 非价值性的粒子和浮字随机 |
| 掷骰最终结果、战斗结算、彩票结果 | 战斗回放速度和跳过表现 |
| 离线时长和收益 | 请求何时由玩家点击发起 |
| 拍卖上架、锁定、扣款、成交 | 搜索表单和详情预览 |
| 聊天身份、禁言、屏蔽和留存 | 本地面板开关、字号 |

## 5. 20 人容量规则

### 5.1 在线定义

账号完成登录且存在有效游戏 WebSocket 会话，计为 1 名在线玩家。前台页面使用应用心跳确认活跃；后台页面优先由浏览器可见性通知切换状态。若整个浏览器窗口被系统暂停、无法发送可见性通知，则心跳满30秒未更新时自动切入后台在线状态，不再注销会话；连接真正中断后才进入30秒重连保护。

```text
认证成功
  ├─ 当前在线 < 20 → 占用名额，进入角色选择
  └─ 当前在线 ≥ 20 → 不占用名额，返回“服务器已满”

连接中断
  ├─ 30 秒内重连且会话有效 → 保留原名额
  └─ 超过 30 秒 → 释放名额，角色进入离线状态
```

| 边界 | 处理 |
|------|------|
| 0 人在线 | 服务正常等待，不运行无必要的逐玩家实时循环 |
| 第 20 人进入 | 成功，占用最后一个名额 |
| 第 21 人进入 | 不进入游戏、不排队；提示“服务器人数已满，请稍后登录” |
| 同账号第二设备 | 新端进入，旧端收到提示后断开；始终只占1个名额 |
| 页面切到后台但仍保持打开 | 继续占用在线名额；开启自动挂机时由服务器继续推进，不因浏览器暂停帧循环而退出 |
| 页面关闭或网络真正中断 | 停止后台逐格推进；保留30秒重连名额，超时后进入公式离线收益 |
| 服务重启 | 所有在线名额清零；客户端重新认证和恢复角色快照 |

性能目标：20 名在线玩家下，普通状态请求的服务端处理时间 P95 小于 200ms；聊天投递 P95 小于 500ms；拍卖价值事务 P95 小于 1s。`[需与程序确认]` 最终阈值以部署机器压测为准。

### 5.2 后台在线挂机

| 状态 | 服务器行为 | 返回页面后的表现 |
|------|-----------|-----------------|
| 自动挂机开启，页面在前台 | 客户端按表现节奏申请掷骰，服务器逐次计算并保存 | 正常播放移动、战斗和奖励表现 |
| 自动挂机开启，页面在后台且连接仍存在 | 可见性通知后立即接管；通知被浏览器暂停时最迟在心跳中断30秒后接管。服务器每2秒最多推进1次掷骰，战斗在该次事务内完整结算 | 不补播后台期间的全部动画，恢复心跳后直接读取最新角色快照并继续前台挂机 |
| 自动挂机关闭，页面在后台 | 不推进地图和战斗，但会话仍计为在线 | 返回时仅同步最新快照 |
| 页面关闭、断网超过30秒或服务重启 | 不再逐格、逐场模拟；按[[战斗系统规则案【定案】]] §11转入最多12小时的公式离线收益 | 重新登录时一次领取离线金币和经验 |

后台推进不建立待补算队列：服务器实际运行时才按2秒节拍推进，单名角色每次节拍最多执行1个游戏命令；20人全部后台挂机时上限为10个核心循环命令/秒。建设格等需要选择的事件沿用[[大地图规则细化案【定案】]] §12的10秒自动选择兜底；条件不成立时本次节拍跳过并在下个节拍重试，不重复发奖。

> 设计柱检验：后台在线挂机满足柱1（切换窗口不损失正常挂机进度）和柱5（无需保持网页焦点）；关闭页面后仍使用批量离线公式，避免微型服务器长期为离线角色逐场模拟。

## 6. 网络命令与失败处理

### 6.1 统一命令规则

每个会改变角色或市场状态的命令必须包含：

| 字段 | 作用 |
|------|------|
| `request_id` | 客户端生成的幂等编号；相同编号重复提交只返回第一次结果 |
| `session_id` | 标识当前登录会话 |
| `character_id` | 标识操作角色，服务端校验归属 |
| `rules_version` | 防止旧客户端按旧规则提交 |
| `expected_revision` | 可选，防止用过期背包或金币状态覆盖新状态 |

### 6.2 成功和失败

| 场景 | 成功 | 失败 |
|------|------|------|
| 普通查询 | 返回分页数据和服务端时间 | 超时可自动重试，不改变资产 |
| 价值操作 | 一个数据库事务内校验、扣除、发放、记流水 | 任一步失败则整笔回滚，返回稳定错误码 |
| 响应丢失 | 用同一 `request_id` 查询或重试，返回原结果 | 不生成第二份奖励、不重复扣款 |
| 客户端版本旧 | 拒绝价值操作并要求刷新网页 | 不尝试兼容未知旧字段 |
| 服务维护 | 拒绝新价值操作，已开始事务完成或回滚 | 客户端展示维护状态并保留输入 |

## 7. 随机与可审计性

| 随机类型 | 算法要求 | 记录要求 |
|---------|---------|---------|
| 掷骰、装备、掉落、彩票 | 服务端安全随机源生成整数或 `[0,1)` 浮点，再按现有权重累计区间抽取 | 记录事件编号、规则版本、结果和关键输入 |
| 战斗命中/暴击/格挡 | 每个判定独立抽样，顺序与 [[战斗系统规则案【定案】]] §4 一致 | 价值结算至少保留摘要，可选保留回放种子 |
| 地图洗牌 | 服务端 Fisher-Yates，每次扩张最多重试既定次数 | 记录地图修订号与最终结果 |
| 聊天/账号会话令牌 | 密码学安全随机字节，不使用游戏随机函数 | 数据库只存令牌摘要，不存明文 |

失败分支：随机服务异常或规则配置缺失时，当前价值操作整体失败并回滚；不允许客户端补随机结果。

## 8. 数据与迁移边界

### 8.1 核心数据所有权

| 数据 | 所有者 | 最低约束 |
|------|--------|---------|
| 账号 | 账号服务 | 登录名唯一；密码只存哈希 |
| 角色 | 账号 | 每账号1个角色；角色名全服唯一；名称权重1~14 |
| 装备实例 | 角色/拍卖托管 | 全局唯一编号，同一时刻只能有一个所有者状态 |
| 金币 | 角色 | 64 位整数，范围 `0 ~ 9,000,000,000,000,000`，所有变化记流水 |
| 聊天消息 | 频道和发送角色 | 服务器分配消息编号和时间 |
| 拍卖订单 | 卖家角色 | 状态机单向迁移，成交不可重复执行 |

### 8.2 本地存档迁移

现有本地JSON不迁移。联网服所有玩家从新角色开始；旧本地代码只作为历史参考和可复用规则回归，不再维护或交付桌面模式，不向服务端上传资产。

## 12. 设计柱检验

| 设计决策 | 设计柱 | 检验 |
|---------|--------|------|
| 保留个人地图，只共享社交与市场 | 柱1、柱4、柱5 | 保留挂机和格子策略，不强迫玩家同步在线 |
| 价值结果服务端权威 | 柱2、柱6 | Build 与交易资产可信，市场不会被客户端篡改摧毁 |
| 拍卖行在资产权威化后开发 | 柱6 | 先保证资产唯一和金币守恒，再开放流通 |
| 离线采用12小时批量公式 | 柱1、柱5 | 回归有收益，同时避免持续模拟造成维护负担 |
| 只维护Godot浏览器客户端 | 柱2、柱4、柱5 | 复用原版Build与地图表现，停止重复桌面交付，不擅自简化玩法 |
| 首版ZeroTier私网同源入口 | 柱5、柱6 | 玩家直接浏览器访问；服主统一配置加密网络与监听，真正公网另加HTTPS/WSS |
| 后台在线挂机由服务器推进 | 柱1、柱5 | 浏览器后台限帧不再中断成长；回到页面直接同步权威结果，不要求补播积压动画 |

总纲已恢复柱6“玩家经济”，与聊天、拍卖和服务端权威资产规则一致。
